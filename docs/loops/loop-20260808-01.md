## 1. 目的

第1段階ではPDFそのものを分割せず、現在のPDF.js・Firebase Storage・Firestore構成を保ちながら、100MiB・500ページ級のPDFで次を満たすことを目指す。

- 大容量アップロード中に画面が無反応にならず、進捗・取消・再試行ができる。
- PDF.jsとブラウザー標準PDFビューアーが同じPDFを同時に取得しない。
- 表示対象ページと限定されたサムネイルだけを描画する。
- PDF切替・資料削除・画面離脱後にBlob URL、PDF文書、描画タスクが残り続けない。
- Range Requestを利用できる配信環境では、全体ダウンロード完了を待たずに先頭ページを表示する。
- 資料パネル内でPDF・画像の「資料名」を変更できる。
- 資料名変更ではStorage上のオブジェクトをcopy/deleteせず、参照切れや大容量ファイルの再転送を起こさない。

## 3. 成功条件

### 3.1 自動テストで固定する条件

- PDF.jsのロード状態が`idle / loading / ready / error`として一意に決まる。
- `loading`中に`<object>`をDOMへ追加しない。
- エラー時の外部表示はユーザーの明示操作でのみ開ける。
- 文書切替、読込失敗、unmountで古い`PDFDocumentProxy`を`destroy()`する。
- ページ描画の完了・取消後に安全なタイミングでページ資源を解放する。
- Blob URLは、永続URLへの置換、資料削除、セッション破棄のいずれでも一度だけrevokeされる。
- アップロード進捗が0〜100%へ正規化され、取消・再試行・失敗を状態として表現できる。
- FirestoreメタデータはStorageアップロード完了後にのみ作成される。
- メタデータ作成失敗時は直前に作成したStorageオブジェクトの補償削除を試みる。
- 500ページでもサムネイルの同時マウント上限を既存の表示窓以内に保つ。
- `displayName`未設定の既存資料は`fileName`を表示する。
- 資料名変更で`storagePath`、`fileName`、`ownerUid`、`noteId`等が変わらない。
- Firestore Rulesは所有者による有効な`displayName`だけを許可し、他項目の同時変更を拒否する。

### 3.2 実測で判定する条件

基準環境を「最新安定版Chrome、メモリ8GB以上、100Mbps相当、Firebase Storageからの取得」とし、以下をGo/No-Go条件にする。PDFの内部構造に依存するため、自動テストだけで合格扱いにしない。

- 100MiB・500ページの代表PDFをアップロードでき、進捗が継続更新される。
- アップロード中に資料選択、スクロール、取消操作が可能である。
- Range対応時はNetworkで`Range`要求と`206 Partial Content`を確認できる。
- 同じPDFに対してPDF.jsと`<object>`による二重の全体取得が発生しない。
- 先頭表示、末尾ページへの移動、連続20ページ移動でクラッシュしない。
- 3種類以上の代表PDFを5回切り替えた後、JS heapが切替回数に比例して増加し続けない。
- 500ページのために500個のCanvasを同時生成しない。
- Range非対応時には進捗付きで待機でき、失敗時に再試行または別画面表示を選べる。

目安値として、Range対応の代表PDFでは初回ページ表示10秒以内、5回切替後のheap増加300MiB未満を狙う。ただしPDF内の超高解像度画像や破損構造によって結果が大きく変わるため、最終判断は代表コーパス全体で行う。

## 5. 設計方針

### 5.1 PDFの取得と描画

PDF.jsを唯一の埋め込み表示経路にする。`TextbookPreview.vue`は次の状態だけを描画する。

```text
idle     -> 資料未選択
loading  -> 読込表示 + 進捗 + 取消可能なら取消
ready    -> Canvasプレビュー + ページ操作
error    -> エラー + 再試行 + 「別画面で開く」
```

`<object data="...">`は自動フォールバックに使わない。ブラウザー標準PDFビューアーを使う場合は、エラー画面のリンクをユーザーが明示的に選んだときだけ別タブで開く。

PDF.jsのRange取得は配信元・CORS・ブラウザー・PDF内部構造に依存する。実装ではRangeを「保証」せず、PDF.jsの既定挙動を壊さない範囲で`rangeChunkSize`と進捗コールバックをアダプターの設定として扱う。合格確認ではNetwork上の`Range`と`206`を必ず実測する。

### 5.2 資源の所有権

| 資源 | 所有者 | 解放タイミング |
|---|---|---|
| `PDFDocumentProxy` | `usePdfDocument` | 文書切替、失敗、unmount |
| `RenderTask` | 描画composable | ページ切替、再描画、unmount |
| `PDFPageProxy`の描画資源 | PDF描画アダプター | RenderTask完了・取消後 |
| Blob URL | `objectUrlRegistry` | 永続URLへ置換、資料削除、セッション破棄 |
| Firebase UploadTask | upload adapter | 完了、取消、失敗時に購読解除 |

`TextbookPanel.vue`へ個別のcleanup処理を追加し続けず、PDF文書、Blob URL、UploadTaskごとに専用composableまたはドメインサービスを設ける。現在の`TextbookPanel.vue`は既に約384行のため、500行を超える変更計画にはしない。

### 5.3 再開可能アップロード

Repositoryの公開契約にはFirebase固有の`UploadTask`を漏らさず、次のような中立的な制御口を追加する。

```ts
type UploadProgress = {
  bytesTransferred: number
  totalBytes: number
  ratio: number
}

type SaveTextbookOptions = {
  onProgress?: (progress: UploadProgress) => void
  signal?: AbortSignal
}

save(input, user, options?: SaveTextbookOptions): Promise<TextbookMetadata>
```

Firebase実装では`uploadBytesResumable`を使用し、`AbortSignal`をUploadTaskの`cancel()`へ接続する。アップロード完了後にだけFirestoreへメタデータを書き込む。Firestore書込に失敗した場合は、その処理で作成したStorageオブジェクトだけを補償削除する。補償削除にも失敗した孤児は、Notebook削除で導入済みの孤児クリーンアップ方針へ記録・回収できる形にする。

### 5.4 大容量の品質保証範囲

- 「Firebaseへ保存可能な最大サイズ」と「ブラウザーで品質保証するサイズ」を分ける。
- 第1段階の代表保証ケースを100MiB・500ページとする。
- 100MiBまたは500ページを超える場合は拒否ではなく、処理時間と端末メモリに関する注意を表示する。
- ハード上限の引下げは実測結果と利用実態を見て別途判断する。
- 巨大な単一ページ画像、破損PDF、暗号化PDFを通常文書とは別の失敗ケースとして確認する。

### 5.5 資料名変更

ユーザーが変更するのはStorageの実ファイル名ではなく、資料パネルで見える表示名である。

```ts
type FileTextbookMetadata = {
  fileName: string       // アップロード時の元ファイル名。不変
  displayName?: string   // ユーザー編集可能な資料名
  storagePath: string    // 不変
  // ...既存項目
}

const visibleName = metadata.displayName ?? metadata.fileName
```

この方式を選ぶ理由は次の通り。

- 100MiB級ファイルのrenameをStorageのcopy/deleteで実現すると遅く、途中失敗時の整合性管理も増える。
- 既存の`storagePath`、ダウンロードURL、参照を維持できる。
- Firestoreの小さな1項目更新だけなので楽観更新とロールバックが容易。
- `displayName`をoptionalにすることで既存データを移行なしで読み込める。

資料名のルール:

- 前後空白を除去して保存する。
- 1〜120文字。
- 改行、NUL、その他の制御文字を拒否する。
- PDF・画像だけを対象にし、ブックマークは今回対象外。
- `saving`または`error`状態の資料は、保存状態が確定するまで変更不可。
- Enterで保存、Escapeで取消、フォーカスを失うだけでは暗黙保存しない。
- 同じ名前への変更はFirestoreへ書き込まず成功扱いにする。

### 5.6 Firestore Security Rules

既存ルールはmaterialスキーマを`keys().hasOnly(...)`で制限し、更新時の`affectedKeys()`を空集合に限定している。次のように変更する。

- PDF・画像スキーマにoptionalな`displayName`を追加する。
- `displayName`が存在する場合だけ文字列、1〜120文字、禁止文字なしを検証する。
- updateでは`diff(resource.data).affectedKeys().hasOnly(['displayName'])`のみ許可する。
- `ownerUid`、`noteId`、`storagePath`、`fileName`、`materialId`、種別等は不変のままにする。
- 所有者かつ有効なNotebook配下という既存条件を維持する。
- create時も同じ名前検証を適用する。
- 旧PDFスキーマと現行ファイルスキーマの両方で後方互換を確認する。
- Storage Rulesはオブジェクトを変更しないため、今回変更しない。

## 7. 詳細TDDループ

各Loopは15分以内を目安に、必ず「失敗するテスト → 最小実装 → テスト → リファクタ → 再テスト」の順で行う。15分を超える場合は、その場で実装範囲を分割する。

### Loop 1: DESIGN.mdへ仕様を追加

1. `designSsoT`へ、巨大PDFのloading/error/progressと資料名編集仕様が未記載なら失敗する検査を追加する。
2. `DESIGN.md`の資料パネル節に、進捗、失敗、再試行、資料名編集、Storage名不変を追記する。
3. `npm run test -- designSsoT`を実行する。
4. 「ファイル名」「表示名」の混在を整理し、ユーザー向け用語を「資料名」へ統一する。
5. 同じテストを再実行する。

### Loop 2: PDF読込状態モデルを追加

1. `idle/loading/ready/error`と進捗の遷移テストを追加して失敗を確認する。
2. UI非依存の`pdfLoadState`と遷移関数を最小実装する。
3. `npm run test -- pdfLoadState`を実行する。
4. 不可能な状態を型で表現できないdiscriminated unionへ整理する。
5. 同じテストを再実行する。

### Loop 3: 自動`object`表示を廃止

1. loading中に`object`が存在せず、loading UIが表示されるテストを追加する。
2. `TextbookPreview.vue`を状態モデルへ接続し、自動`object`分岐を削除する。
3. `npm run test -- TextbookPreview`を実行する。
4. 重複する条件式をcomputedへ集約する。
5. 同じテストを再実行する。

### Loop 4: 明示的な代替表示を追加

1. error時だけ「再試行」「別画面で開く」が現れ、通常時は現れないテストを追加する。
2. 外部表示リンクへ`target="_blank"`と`rel="noopener noreferrer"`を設定する。
3. `npm run test -- TextbookPreview`を実行する。
4. エラー表示が大きくなる場合は`TextbookPreviewError.vue`へ自然に分離する。
5. 同じテストを再実行する。

## 9. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| PDF内部構造がRange表示に不向き | 100MB全体取得まで初回表示が遅い | 代表コーパスで計測し、第1Bのlinearization判断へ送る |
| Range応答が環境依存 | 開発環境だけ速く本番で遅い | Emulatorと実Storageの両方でNetworkを確認する |
| 超高解像度画像ページ | 1ページだけでメモリを圧迫 | 既存Canvas上限を維持し、縮小倍率とエラーUIを確認する |
| Blob URLの早すぎるrevoke | 保存前プレビューが壊れる | 所有権をregistryへ限定し、置換時だけ解放する |
| 文書cleanupの早すぎる実行 | 描画中エラーや白紙化 | RenderTask settle後の順序をテストで固定する |
| upload取消と完了が競合 | Firestoreだけ/Storageだけの不整合 | 状態遷移を一意化し、完了後のcancelをno-opにする |
| 補償削除も失敗 | Storage孤児が残る | エラーを観測可能にし、定期孤児クリーンアップで回収する |
| Rulesのoptional field追加漏れ | 旧資料または新規保存が拒否される | 旧/現行スキーマ双方のcreate/updateをテストする |
| 楽観rename失敗 | UI名とFirestore名がずれる | 旧値を保持し、失敗時にロールバックして通知する |
| Panelへのロジック集中 | 保守性とテスト性が低下 | upload/rename/lifecycleをcomposableへ分割する |

## 11. 第1B段階への判断ゲート

次のいずれかが代表コーパスで再現する場合は、分割実装へ直行せず、まずqpdf linearization等の非破壊な前処理を別計画にする。

- Range対応にもかかわらず、100MiB PDFの先頭ページ表示が目安10秒を大きく超える。
- xrefや主要オブジェクト配置のため、PDF全体に近い取得が毎回必要になる。
- ブラウザー側の資源解放後も、代表PDFで安定したページ移動ができない。
- 3種類以上の代表PDFのうち2種類以上が成功条件を満たさない。

第1B段階の候補:

1. 原本は不変で保存する。
2. 非同期ワーカーでqpdf `--linearize`済みの表示用派生ファイルを作る。
3. Firestoreに`processing/ready/failed`と派生ファイルのパスを記録する。
4. Viewerはready後に派生ファイルを使い、downloadは原本を使えるようにする。
5. 派生生成失敗時は今回整備する分割なしViewerへフォールバックする。

現リポジトリにはPDF処理用コンテナやqpdf実行基盤がないため、第1段階へ混在させない。PDF分割はlinearizationでも解決できない実測課題が残った場合の第2段階候補とする。

## 12. ロールバック方針

- PDF表示変更は状態モデルとViewer単位で戻せるコミットに分ける。
- resumable uploadはRepository契約とFirebase adapterを別コミットにし、問題時に旧upload実装へ戻せるようにする。
- `displayName`はoptional追加なので、UIを戻しても既存`fileName`表示へ自然にfallbackできる。
- renameはStorageを変更しないため、機能停止時もデータ移動の巻き戻しは不要。
- Rulesを戻す場合、既に存在する`displayName`は読取を妨げないことを先に確認する。更新だけを停止できる形にする。
- 補償削除は「今回作成した正確なStorage path」に限定し、既存資料を削除対象にしない。
