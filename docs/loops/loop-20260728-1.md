## Goal / Scope

`docs/proposal.md` の「教科書と対話的に学べる環境」を、認証認可を含む最初の MVP として以下に切り出す。

- Firebase Authentication の Google 認証で、新規登録とログインを同一フローで扱える。
- 未ログインユーザーは AIチャットやAI機能を使えない。API利用料を制限できないため、AI実行はログイン必須にする。
- ログイン済みユーザーは AIチャットを 100回/日 まで使える。
- 未ログインユーザーの教材アップロードは 10MB までに制限し、保存履歴には残さない一時利用に留める。
- ログイン済みユーザーの教材アップロードは 5GB までに制限し、本人の Storage / Firestore 配下へ保存する。
- ノート保存、アップロード済み教材の履歴、AIチャット履歴、ホワイトボード履歴など「保存・履歴を見る」機能はログインユーザーのみ利用できる。
- ログイン後は、ノート、アップロード教材、ホワイトボードページ、AIチャット履歴、図表コード状態を `request.auth.uid` 単位で分離する。
- Firestore は `users/{userId}/...` 配下、Storage は `users/{userId}/...` 配下を基本パスにし、Rules で `userId == request.auth.uid` を必須にする。
- ノート一覧画面で自分の数学ノートを作成、検索、複製、削除、お気に入り設定できる。
- ノートを開くと、教科書、ホワイトボード、AIチャット、図表・コードの4パネルを持つワークスペースを表示できる。
- 各パネルは最初は軽い状態管理と空状態表示までに留め、PDF解析、手書き描画、AI実行、コード実行は後続ループへ分離する。

今回の非対象:

- Google 以外の認証プロバイダ。
- 複数ユーザー共有、共同編集、閲覧権限の委譲。
- PDFアップロード本体、ページサムネイル生成、OCR。
- ホワイトボードの本格キャンバス描画、手書き数式認識。
- Realtime API / GPT-Live 連携の実通信。
- Python / JavaScript コード実行環境。
- 共有URL、権限設定、PDF/画像エクスポート。

## Assumptions and Risks

- 既存アプリは Vue 3、Pinia、Vue Router、Vitest、Firebase を使うため、新規実装もこの構成に合わせる。
- `src/utils/firebase.ts` には `auth` と `db` が既にあり、`src/utils/SocialLogin.ts` には Google サインインの入口がある。計画ではこれをテスト可能なサービス境界へ整理する。
- Google 認証では Firebase Authentication 上の初回サインインが新規登録を兼ねるため、画面文言は「Googleで登録・ログイン」とする。
- 既存ルーティングは `/:lang` とルートなしの両方を持つため、新しい画面も `routeChildren` に追加する。
- 現在の Firestore 設定はデフォルト DB 前提なので、repository では `getFirestore()` の通常接続を前提にする。
- 現在の `firestore.rules` には `message` / `test` の緩い read/create があり、MVP 実装前にユーザー別ルールへ置き換える計画を入れる。
- 未ログインアップロードの 10MB 制限はクライアント側だけで信用しない。永続保存しない前提でも、Functions / Storage Rules / upload adapter のどこで強制するかをテストで固定する。
- 現在の `storage.rules` はログイン済みなら全ファイルにアクセスできるため、教材アップロード前に `users/{uid}/...` 制限と 5GB 上限へ置き換える計画を入れる。
- AIチャットの 100回/日はクライアント状態だけでは回避可能なため、最終的には Firebase Functions 側で `uid + date` 単位のカウントを検証する。
- Security Rules では `ownerUid` のようなユーザー入力フィールドだけに権限を依存させない。パス上の `{userId}` と `request.auth.uid` を権限の主軸にする。
- 15分単位を守るため、各ループでは UI、状態、外部連携、Rules を同時に広げない。
- CSS は既存の Tailwind 中心の書き方に寄せ、グローバル CSS 追加は最小限にする。

## Detailed Loops

### Loop 1: 認証状態モデルを固定

- Objective: Firebase User からアプリが使う最小の `AuthUser` を作り、ログイン中、未ログイン、判定中を扱えるようにする。
- TDD test to add or change: `tests/auth/authState.test.ts` を追加し、Firebase User 風オブジェクトから `uid`, `email`, `displayName`, `photoURL` が抽出されること、未ログインが `null` になることを確認する。
- Minimal implementation steps:
  - `src/features/auth/types.ts` を追加する。
  - `src/features/auth/mapFirebaseUser.ts` を追加する。
  - 既存 `src/store/index.ts` の `user` を直接広げる前に、アプリ用型へ変換する方針を固定する。
- Unit test command to run after the task: `npm run test -- authState`
- Refactoring checkpoint: Firebase SDK の `User` 型を画面コンポーネントへ広げすぎない。
- Completion criteria: 認証状態の最小モデルがテストで固定される。

### Loop 2: Google認証サービスを固定

- Objective: Googleアカウントによる新規登録・ログインをサービス関数として扱えるようにする。
- TDD test to add or change: `tests/auth/googleAuth.test.ts` を追加し、Google provider で `signInWithPopup` が呼ばれること、エラーが戻り値で扱えることを確認する。
- Minimal implementation steps:
  - 既存 `src/utils/SocialLogin.ts` の Google 処理を `src/features/auth/googleAuth.ts` へ寄せる。
  - `GoogleAuthProvider` の scope は `email` を維持する。
  - Facebook 認証は MVP 非対象としてこのループでは触らない。
- Unit test command to run after the task: `npm run test -- googleAuth`
- Refactoring checkpoint: provider 生成、Firebase 呼び出し、画面遷移を別責務に分ける。
- Completion criteria: Google で登録・ログインするためのサービス境界がテストで固定される。

### Loop 3: 認証画面を整備

- Objective: `Account.vue` を Google 登録・ログイン画面として整え、成功時に自分のノート一覧へ遷移する。
- TDD test to add or change: `tests/views/AccountPage.test.ts` を追加し、未ログイン時に Google ボタンが表示され、クリックで認証サービスが呼ばれ、成功時に `/notes` へ遷移することを確認する。
- Minimal implementation steps:
  - `src/views/Account.vue` の文言を「Googleで登録・ログイン」に寄せる。
  - 成功時の遷移先を `/mypage` ではなく MVP の `/notes` にする。
  - エラー表示の最小 UI を追加する。
- Unit test command to run after the task: `npm run test -- AccountPage`
- Refactoring checkpoint: 画面はサービスの戻り値を扱うだけにし、Firebase SDK を直接 import しない。
- Completion criteria: ユーザーが Google アカウントで登録・ログインを始められる。

### Loop 4: 認可ポリシーを追加

- Objective: 未ログインとログイン済みで使える機能差を `AccessPolicy` として固定する。
- TDD test to add or change: `tests/auth/accessPolicy.test.ts` を追加し、未ログインは AI不可、保存・履歴不可、アップロード10MBまで、ログイン済みはAI 100回/日、アップロード5GBまで、保存・履歴可になることを確認する。
- Minimal implementation steps:
  - `src/features/auth/accessPolicy.ts` を追加する。
  - `canUseAi`, `canPersistHistory`, `getUploadLimitBytes`, `getDailyAiLimit` を純粋関数で定義する。
  - `src/features/auth/authGuard.ts` を追加する。
  - `src/router/index.ts` で `meta.requiresAuth` と `meta.requiresPersistentUserData` を使える構造にする。
  - 既存 `requireLogin` は後方互換を残すか、新ガードへ寄せる。
- Unit test command to run after the task: `npm run test -- accessPolicy`
- Refactoring checkpoint: `/:lang` 付き URL でも遷移先が壊れないか確認する。
- Completion criteria: AI、保存、履歴、アップロード上限の認可判定が画面に依存しない形で固定される。

### Loop 5: ユーザー別データパスを定義

- Objective: ノート、教材、AI履歴、ホワイトボード、図表コードの保存先パスを `uid` 単位で固定する。
- TDD test to add or change: `tests/data/userDataPaths.test.ts` を追加し、`uid` と各 ID から Firestore / Storage パスが生成されることを確認する。
- Minimal implementation steps:
  - `src/features/user-data/userDataPaths.ts` を追加する。
  - Firestore パス例を `users/{uid}/notes/{noteId}`, `users/{uid}/notes/{noteId}/chatMessages/{messageId}`, `users/{uid}/notes/{noteId}/whiteboardPages/{pageId}` にする。
  - Storage パス例を `users/{uid}/textbooks/{textbookId}/{fileName}` にする。
- Unit test command to run after the task: `npm run test -- userDataPaths`
- Refactoring checkpoint: パス文字列を repository や component に直書きしない。
- Completion criteria: すべての個人データが `uid` 配下に置かれる設計になる。

### Loop 6: Firestore Rules計画を追加

- Objective: 他ユーザーのノート、教材メタデータ、チャット履歴、ホワイトボードページを読めない Firestore Rules を先にテストする。
- TDD test to add or change: `tests/security/firestoreRules.test.ts` を追加し、本人は `users/{uid}/...` を read/write でき、他人と未ログインは拒否されることを確認する。
- Minimal implementation steps:
  - 必要なら `@firebase/rules-unit-testing` を devDependency に追加する。
  - `firestore.rules` を `match /users/{userId}` 中心の構造へ変更する計画にする。
  - `create` と `update` の両方で型、必須フィールド、サイズ上限、`userId == request.auth.uid` を確認する。
  - 既存の緩い `message` / `test` ルールは削除対象にする。
- Unit test command to run after the task: `npm run test -- firestoreRules`
- Refactoring checkpoint: 権限判定を `request.resource.data.ownerUid` だけに依存させない。
- Completion criteria: Firestore 上で本人以外が個人データを読めないことをテストで固定する。

### Loop 7: Storage Rules計画を追加

- Objective: ログイン済み教材ファイルを本人だけが読め、5GBまで保存できる Storage Rules にする。未ログインの一時アップロードは10MBまでに制限し、永続履歴から分離する。
- TDD test to add or change: `tests/security/storageRules.test.ts` を追加し、本人は `users/{uid}/textbooks/...` を5GBまで read/write でき、他人と未ログインは拒否されることを確認する。未ログイン一時アップロードを扱う場合は 10MB 超過が拒否されることも確認する。
- Minimal implementation steps:
  - `storage.rules` を `match /users/{userId}/textbooks/{allPaths=**}` 中心に変更する計画にする。
  - ログイン済みユーザー向けに PDF の contentType と 5GB のファイルサイズ上限を定義する。
  - 未ログイン向け一時アップロードを Storage に置く場合は `temporary/{sessionId}/...` のような別パスにし、10MB 上限と短期削除前提を明記する。可能なら未ログインはブラウザ内一時利用に留める。
  - その他のパスは `allow read, write: if false` にする。
- Unit test command to run after the task: `npm run test -- storageRules`
- Refactoring checkpoint: ログイン済みなら全ファイル可、というルールを残さない。
- Completion criteria: Storage 上で他ユーザーの教材ファイルを読めず、認証状態ごとのアップロード上限がテストで固定される。

## Verification Strategy

- 各ループ直後は表に記載した対象テストだけを実行する。
- 認証まわりを触った Loop 1-4 の後は、Google 認証の成功系だけでなく、キャンセルやエラー系の表示も確認する。
- 認可ポリシーを触った後は、未ログインAI不可、ログイン済みAI100回/日、未ログインアップロード10MB、ログイン済みアップロード5GB、保存・履歴はログイン必須の5条件を必ず確認する。
- Security Rules を触った Loop 6-7 の後は、Rules unit test に加えて emulator で本人、他人、未ログインの3ケースを確認する。
- UI コンポーネントを触ったループでは、対象テストに加えて `npm run test -- <component-or-view-name>` を再実行する。
- Loop 4、Loop 15、Loop 16、Loop 24 の後は `npm run build` を実行し、ルーティングと型チェックの破綻を確認する。
- Firestore / Storage repository 境界を追加した後は、実 Firebase ではなく fake repository で契約テストを通す。
- MVP 完了時にまとめて実行するコマンド:

```bash
npm run test
npm run build
```

- Rules を実装した後に確認するコマンド候補:

```bash
npx -y firebase-tools@latest emulators:exec --only firestore,storage "npm run test -- firestoreRules storageRules"
```

## Rollback / Follow-up Notes

- 認証関連で問題が出た場合は、まず `src/features/auth/*` と route guard の変更を切り戻し、既存 `Account.vue` の Google サインイン入口を残して原因を分離する。
- Rules 変更で開発が詰まる場合でも、全開放に戻さず、emulator 上で failing test を増やして必要な許可だけを追加する。
- 途中で UI が大きくなりすぎた場合は、まず `src/features/*` の純粋関数と store を残し、画面コンポーネントだけを戻せる単位にする。
- Firestore のデータ構造が確定するまでは migration 前提のフィールドを増やさず、repository interface の契約テストを優先する。
- PDF、AI、コード実行はそれぞれ別の開発ループに分ける。特に AI 通信は Firebase Functions 経由にするか、Web から直接呼ぶかを設計判断として別途固定する。
- 共有、権限、エクスポートは Firestore Security Rules と Storage Rules の追加設計が必要なため、本人専用 MVP 完了後の独立計画にする。
