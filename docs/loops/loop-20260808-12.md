| Loop | Task | User-facing summary | Unit test | Refactor checkpoint |
| --- | --- | --- | --- | --- |
| 1 | 削除確認仕様をSSoTへ追加 | 削除前に確認し、「削除する」を選んだ場合だけ削除する仕様を固定します。 | `npm run test -- designSsoT` | 確認文言と危険操作の見た目を重複定義しない |
| 2 | 削除確認ダイアログを追加 | ノート名と削除の影響を確認してから、削除またはキャンセルを選べるようにします。 | `npm run test -- NoteDeleteConfirmDialog` | ダイアログ固有の状態・CSSを部品内に閉じる |

各Loopは15分以内を目安とし、テスト追加（Red）→最小実装（Green）→責務内の整理（Refactor）の順で完了させる。

## 目的・スコープ

### 参照元

- 要望: ノートブックの削除ボタンを押しても即時削除せず、確認後に「削除する」を選んだ場合だけ削除する。
- デザインSSoT: `DESIGN.md` 7.3 Danger、7.7 Dialog。
- 現行の削除UI: `src/components/notes/NoteCard.vue`。
- 現行の利用画面: `src/components/home/HomeNotesSummary.vue`、`src/views/NotesListView.vue`。
- 現行の削除処理: `src/features/notes/notesStore.ts`、`src/features/notes/firestoreNotesRepository.ts`、`functions/src/functions/notes/`。

### 目的

- ノートカードの「削除」を押した時点では、`delete`イベントも永続データの削除も開始しない。
- 「本当に削除していいですか？」という確認と、削除対象のノート名、関連データも削除される旨を表示する。
- 利用者が明示的に「削除する」を選んだ場合だけ、既存のノート削除フローを開始する。
- 「キャンセル」、背景クリック、`Esc`ではダイアログだけを閉じ、ノートと関連データを維持する。
- HOMEとノート一覧で、共有されている`NoteCard`を通して同じ安全な削除操作を提供する。

### 最小の有用な完了状態

1. ノートカードの「削除」を押すと、対象ノート名を含む削除確認ダイアログが開く。
2. ダイアログが開いただけでは`delete`イベントが発火しない。
3. 「キャンセル」、背景クリック、`Esc`のいずれでも削除されない。
4. 赤い確定ボタン「削除する」を押した場合だけ、対象ノートIDで`delete`イベントが1回発火する。
5. マウスを使わなくてもダイアログの内容を確認し、安全にキャンセルまたは確定できる。

### 対象外

- `notesStore`、Firestore repository、Callable Functionsにある削除順序や再試行処理の変更。
- 削除済みノートのごみ箱、保持期間、復元機能の追加。
- PDF、画像、手書き、AIチャットだけを個別に残す選択肢の追加。
- 削除中プログレス、成功トースト、失敗時UIの再設計。
- `NoteCreateModal`など、今回と無関係な既存ダイアログの共通基盤化や全面リファクタリング。

## 前提・現状・リスク

### 前提と仕様判断

- 確認タイトルは「本当に削除していいですか？」、確定ボタンは要望どおり「削除する」、非破壊操作は「キャンセル」とする。
- 本文には対象ノート名と、紐づくPDF・画像・手書き・AIチャットも削除され、取り消せないことを表示する。
- 誤操作を避けるため、ダイアログを開いた直後のフォーカスは「キャンセル」に置く。「削除する」を既定のEnter操作にしない。
- ダイアログは`role="dialog"`、`aria-modal="true"`、見出しとの`aria-labelledby`関連を持つ。
- 背景クリックと`Esc`は「キャンセル」と同じ扱いにする。確定操作は「削除する」ボタンの明示的な操作だけに限定する。
- `DESIGN.md`に従い、オーバーレイは黒20%、本体はRaised、確定ボタンだけを赤背景＋白文字にする。
- ダイアログ専用CSSは新しいVueコンポーネントの`<style scoped>`へ置き、`src/index.css`や画面全体のCSSへ追加しない。色、影、角丸、余白は既存トークンを再利用する。

### 現行実装との差分

| 領域 | 現行 | 計画後 |
| --- | --- | --- |
| 削除ボタン | `NoteCard`内でブラウザ標準の`globalThis.confirm()`を呼ぶ未コミット差分がある | アプリ内の削除確認ダイアログを開く |
| 確定ボタン | ブラウザ・OS依存で「OK」などになり、「削除する」を保証できない | 常に「削除する」と表示する |
| キャンセル | native confirmのキャンセル | 「キャンセル」、背景クリック、`Esc`で閉じる |
| 見た目 | ブラウザ・OS依存 | `DESIGN.md`の削除確認Dialogに準拠 |
| 削除処理 | 確定後に`delete`イベントを発火 | 同じ既存イベントを専用ダイアログの確定後だけ発火 |

### 主なリスク

- `NoteCard`はHOMEとノート一覧の両方から利用される。確認状態を親画面へ重複実装すると、片方だけ即時削除へ戻る可能性があるため、共有コンポーネント内へ統合する。
- 一覧には複数の`NoteCard`がある。各カードは自分の確認状態とノートIDだけを扱い、別カードを削除しないことをテストで固定する。
- `Esc`用のwindow listenerを解除しないと、カード再描画後にclose処理が重複する。mount/unmountで登録と解除を対称にする。
- 確認ボタンで`delete`をemitした直後に再操作できると二重発火し得る。確定時にダイアログを閉じ、1回の操作につき1回だけemitする契約を固定する。
- 現在の作業ツリーには多数の未コミット差分があり、`NoteCard.vue`と`NoteCard.test.ts`にもnative confirmの途中実装がある。実装時はstash、reset、上書きをせず、その差分を専用ダイアログ方式へ置き換える。

## 詳細ループ

### Loop 1: 削除確認仕様をSSoTへ追加

- Objective: ノートブック削除の確認手順と文言を`DESIGN.md`へ記録し、UI実装の判断元を一つにする。
- TDD test to add or change:
  - `tests/docs/designSsoT.test.ts`へ、ノートブック削除は確認ダイアログを経由し、「削除する」の選択時だけ削除する旨が記載されていることを確認するケースを追加する。
  - キャンセル可能であることと、削除確認の確定ボタンが赤であることを仕様上の契約として固定する。
- Minimal implementation steps:
  - `DESIGN.md` 7.7 Dialogまたはノート一覧の画面仕様へ、ノートブック削除確認の表示条件、ボタン文言、キャンセル動作を追記する。
  - 既存の「削除確認は赤の確定ボタン」と重複する色指定は増やさず、ノート固有の操作順だけを追記する。
- Unit test command to run after the task: `npm run test -- designSsoT`
- Refactoring checkpoint: 汎用Dialogの視覚仕様とノート削除固有の文言・挙動を同じ段落へ混在させず、既存章の責務に沿って配置する。
- Completion criteria: `DESIGN.md`だけから「削除を押す → 確認する → 『削除する』で確定」という順序とキャンセル条件を再現でき、テストが成功する。

### Loop 2: 削除確認ダイアログを追加

- Objective: 削除対象と影響を明示し、安全に確定またはキャンセルできるノート専用ダイアログを作る。
- TDD test to add or change:
  - `tests/components/NoteDeleteConfirmDialog.test.ts`を追加する。
  - `role="dialog"`、`aria-modal="true"`、見出し関連、対象ノート名、取り消せない旨を表示することを確認する。
  - 「キャンセル」、背景クリック、`Esc`で`close`だけをemitし、`confirm`をemitしないことを確認する。
  - 「削除する」で`confirm`を1回emitすることを確認する。
  - mount後に「キャンセル」へフォーカスが移り、unmount後は`Esc`へ反応しないことを確認する。
- Minimal implementation steps:
  - `src/components/notes/NoteDeleteConfirmDialog.vue`を追加し、`noteTitle` propと`close` / `confirm` emitを定義する。
  - 既存の`AppButton`を再利用して「キャンセル」と「削除する」を表示し、確定ボタンへダイアログ固有の赤背景＋白文字を適用する。
  - 背景クリック、`Esc`、初期フォーカス、listenerの後始末をコンポーネント内で管理する。
  - 小画面でも本文と2ボタンがviewport外へ欠落しない幅・余白を、同コンポーネントの`<style scoped>`で定義する。
- Unit test command to run after the task: `npm run test -- NoteDeleteConfirmDialog`
- Refactoring checkpoint: `NoteCreateModal`や`WhiteboardDrawingDialog`を同時に共通化せず、今回の削除確認に必要な責務だけを新コンポーネントへ置く。新しいグローバルCSSや固定色を追加しない。
- Completion criteria: ダイアログ単体で確定・3種類のキャンセル・初期フォーカス・listener解除がテストされ、確定ボタンの表示文言が「削除する」になっている。

### Loop 3: ノートカードへ確認操作を統合

- Objective: ノートカードの削除イベントを、専用ダイアログで明示的に確定した後だけ発火させる。
- TDD test to add or change:
  - `tests/components/NoteCard.test.ts`の`globalThis.confirm` stubを削除し、アプリ内ダイアログを操作するテストへ置き換える。
  - 「削除」を押した直後はダイアログが表示されるだけで、`delete`がemitされないことを確認する。
  - 「キャンセル」後はダイアログが閉じ、再度開け、ノートIDがemitされないことを確認する。
  - 「削除する」で対象ノートIDが1回だけemitされ、ダイアログが閉じることを確認する。
  - 他人のノートでは削除ボタンがdisabledのままで、ダイアログを開けないことを維持する。
- Minimal implementation steps:
  - `NoteCard.vue`へ`isDeleteConfirmOpen`を追加し、削除ボタンではstateを開くだけにする。
  - `NoteDeleteConfirmDialog`を`v-if`で表示し、対象の`note.title`を渡す。
  - `close`ではstateだけを閉じ、`confirm`ではstateを閉じてから既存の`delete`イベントへ`note.id`を1回emitする。
  - `globalThis.confirm()`、eslint抑制コメント、native confirm専用のテストsetupを削除する。
- Unit test command to run after the task: `npm run test -- NoteCard`
- Refactoring checkpoint: 確認文言やキーボード処理は`NoteCard.vue`へ複製せず、カード側は開閉stateと既存イベントの接続だけを担当する。
- Completion criteria: 削除ボタン単独では削除イベントが発火せず、「削除する」を選んだ場合だけ正しいノートIDが1回通知される。

### Loop 4: HOME・ノート一覧の回帰を固定

- Objective: `NoteCard`を利用する2つの入口で、確認前にノートが消えず、確定後だけ既存の削除処理へ接続されることを保証する。
- TDD test to add or change:
  - `tests/views/NotesListView.test.ts`へ、「削除」クリック後は対象ノートが残り、確認ダイアログをキャンセルしても残るケースを追加する。
  - 同テストへ、再度開いて「削除する」を押すと対象ノートだけが一覧から消え、別ノートは残るケースを追加する。
  - `tests/views/HomePage.test.ts`へ、HOMEのノートカードでも削除確認ダイアログが開き、確定前は対象ノートが残るケースを追加する。
  - 必要に応じて`flushPromises()`を使い、既存のInMemory repositoryへの削除完了後にDOMを検証する。
- Minimal implementation steps:
  - 原則として`Home.vue`、`HomeNotesSummary.vue`、`NotesListView.vue`の削除handlerは変更せず、共有`NoteCard`から確定後に届く既存イベントを利用する。
  - テストで配線差異が見つかった場合だけ、イベント名と引数を既存の`deleteNote(noteId)`契約へ揃える最小変更を行う。
- Unit test command to run after the task: `npm run test -- HomePage NotesListView`
- Refactoring checkpoint: HOMEとノート一覧へ別々のmodal stateや確認文言を追加しない。画面側の責務は既存どおりstore actionの呼び出しに限定する。
- Completion criteria: 両画面で確認前・キャンセル後は対象ノートが残り、確定後だけ対象ノートが削除され、他のノートは維持される。

## 検証戦略

### ループごとの自動検証

- 各Loopは、記載したVitestを実装前に失敗させ、最小実装後に成功させる。
- component構造、event、listener、CSS classをrefactorした場合は、同じ絞り込みテストを再実行する。
- 削除Functionsの内部順序は既存テストの責務であり、今回のcomponent testからFirebaseへ接続しない。

### 関連テスト一括

```bash
npm run test -- designSsoT NoteDeleteConfirmDialog NoteCard HomePage NotesListView notesStore
```

### 最終自動検証

```bash
npm run test
npm run lint
npm run build
```

### 手動・ブラウザ確認

1. HOMEで任意のノートの「削除」を押し、対象ノート名と「本当に削除していいですか？」が表示され、一覧からまだ消えないことを確認する。
2. 「キャンセル」、背景クリック、`Esc`をそれぞれ試し、ダイアログだけが閉じてノートが残ることを確認する。
3. ダイアログを再度開き、「削除する」を押して初めて対象ノートが一覧から消えることを確認する。
4. ノート一覧画面でも同じ手順を行い、別のノートが削除されないことを確認する。
5. キーボードだけで削除ボタンを開き、初期フォーカスが「キャンセル」にあり、Tab移動後に「削除する」を選べることを確認する。
6. 390×844とデスクトップ幅で、本文と「キャンセル」「削除する」がviewport外へ欠落しないことを確認する。
7. 確定ボタンだけが赤背景＋白文字で、背景が黒20%オーバーレイ、本体がRaisedになっていることを確認する。
8. 削除失敗を再現できる環境では、既存のエラー表示とoptimistic rollbackが引き続き働くことを確認する。

## ロールバック・フォローアップ

- 問題がある場合は、`NoteDeleteConfirmDialog`の表示と`NoteCard`の開閉stateだけを切り戻せる。`notesStore`、Firestore、Storage、Functionsの削除処理やデータ形式には変更を加えない。
- UIを切り戻す際も即時削除へ戻さず、少なくとも既存のnative confirmを維持して誤削除を防ぐ。
- この計画では削除済みデータの復元は提供しない。ごみ箱や保持期間が必要になった場合は、Firestore/Storageのライフサイクルを含む別計画にする。
- 複数のダイアログでフォーカストラップやbody scroll lockが必要になった場合は、既存Dialog群を横断する共通プリミティブ化を別タスクで検討する。
