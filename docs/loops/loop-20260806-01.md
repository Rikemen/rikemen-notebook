## 目的 / スコープ

資料パネルへ既存のPDFに加えて、PNG・JPG・JPEG画像とブックマークURLを追加し、ログインユーザーはノート単位で永続保存できるようにする。未ログインユーザーは、既存PDFと同様に同一ブラウザセッションのPinia state内だけで一時利用できるようにする。加えて、ホワイトボードのMarkdown・ページ・手書き内容をlocal-firstで即時退避し、Firestore / Storageへ低頻度で自動同期する。

- PDFは現在のページ解析、目次、サムネイル、Canvas preview、ズームを維持する。
- PNG・JPG・JPEGは資料一覧から選択し、資料パネルのpreviewモードで縦横比を保って表示する。
- ブックマークは資料一覧に表示し、行をクリックすると `target="_blank"` で外部ページを開く。
- ブックマークの外部リンクには `rel="noopener noreferrer"` を付ける。
- ホワイトボードのMarkdown previewでは、本文を基準に `### = +2pt`、`## = +4pt`、`# = +6pt` とする。
- Markdown入力は即座にPiniaへ反映し、IndexedDBへ短い間隔で下書き保存する。
- Firestore / Storageへのcloud自動保存は、Markdown・ページ・手書きの種類を問わず「最後の編集から30秒後」に行う。編集のたびにtimerを30秒へ戻し、入力中の定期flushは行わない。
- 手書きはpointer moveごとに送信せず、1ストローク終了後にlocal draftを更新し、最後の編集から30秒後または明示保存でStorageへcheckpointする。
- cloud保存完了かつ追加編集がない場合、右上へ「自動保存済み」と表示する。
- 未保存変更がある場合、右上を「保存する」ボタンへ切り替え、押すと待機中の自動保存を即時flushする。
- 保存中は「保存中…」、失敗時は「再試行」ボタンとエラーを表示し、失敗してもlocal draftを保持する。
- 未保存変更がある状態でブラウザタブやページを閉じる場合は `beforeunload` 警告を表示する。ブラウザ仕様上メッセージは固定される場合がある。アプリ内でホワイトボードパネルを閉じる場合は保存確認を表示し、保存成功後だけ閉じる。
- 既存の `textbook` panel ID、`src/components/textbook/`、`src/features/textbook/`、Firestoreの `materials`、Storageの `materials` パスは変更しない。

### 最小の利用者成果

1. 資料一覧で「ファイル」と「ブックマーク」の追加方法を選べる。
2. PDF、PNG、JPG、JPEGを追加すると、種類の分かる行が現在のノートだけに現れる。
3. PDFは従来どおり、画像は画像用previewで閲覧できる。
4. 有効なブックマーク行をクリックすると新しいタブでページが開く。
5. 再ログイン・再読込後も、ログインユーザーの3種類の資料を復元できる。
6. ホワイトボードpreviewの `#` / `##` / `###` に2pt刻みの視覚階層が付く。
7. ホワイトボード入力は即座に画面とlocal draftへ反映され、最後の編集から30秒後にcloud保存される。
8. cloud未保存中は「保存する」を押して即時保存でき、完了後だけ「自動保存済み」になる。
9. オフラインや保存失敗時も入力を消さず、再接続後または「再試行」で同期できる。
10. cloud未保存のままブラウザページまたはホワイトボードパネルを閉じようとすると、警告または保存確認が表示される。

### 対象外

- SVG、GIF、WebP、HEIC、AVIF、動画、Office文書、ZIPの保存。
- ブックマーク先のタイトル、favicon、OGP画像、本文をサーバーから自動取得する処理。
- ブックマークをアプリ内iframeで表示する処理。
- 画像の回転、切り抜き、圧縮、OCR、複数ページ化、画像用目次。
- 資料の削除、並べ替え、フォルダー分け、共有、公開リンク。
- 既存の内部名称 `textbook` を `material` へ一括リネームするリファクタ。
- 既存PDF metadataを一括更新するmigration。
- Google Docsのような同時共同編集、カーソル共有、文字単位の差分同期。
- 他端末の更新を常時反映する `onSnapshot()` listener。初期MVPは読込時取得とlast-write-winsを採用する。
- pointer moveごとのFirestore / Storage書き込み。
- 保存履歴の全version保持、undo履歴のcloud永続化、監査ログ。

## 前提・現状分析・リスク

### 用語と入力形式

- 依頼文の `jpec` は一般的な拡張子 `jpeg` の誤記として扱う。受け付ける画像は `.png`、`.jpg`、`.jpeg` であり、文字どおりの `.jpec` は対象外とする。
- `.jpg` と `.jpeg` のMIME typeはいずれも `image/jpeg` とする。PNGは `image/png`、PDFは `application/pdf` とする。
- ブックマークURLは `http:` と `https:` だけを許可し、`javascript:`、`data:`、`file:`、相対URL、資格情報付きURLを拒否する。
- ブックマークのタイトルは任意入力とし、空なら正規化後URLのhostnameを表示名にする。タイトルは120文字、URLは2,048文字を上限候補とし、実装前にFirestore Rulesと同じ値へ固定する。
- URL先へのHTTPリクエストは行わない。これにより、SSRF、CORS、取得失敗、外部サイトへの意図しないアクセスを今回の保存処理へ持ち込まない。

### 現行実装との差分

| 領域           | 現行                                  | 計画後                                          |
| -------------- | ------------------------------------- | ----------------------------------------------- |
| 一覧モデル     | PDF前提の `MaterialListItem`          | `pdf / image / bookmark` の判別可能なunion      |
| ファイル入力   | `accept="application/pdf"`            | PDF、PNG、JPEGと `.pdf,.png,.jpg,.jpeg`         |
| 永続化         | PDF本体をStorage、metadataをFirestore | PDF/画像はStorage+Firestore、URLはFirestoreのみ |
| preview        | PDF.js Canvasまたは`object`           | PDFは既存、画像は`img`、URLは外部タブ           |
| 目次・ページ   | 選択資料をすべてPDFとして扱う         | PDFだけに表示し、画像・URLでは無効化            |
| Rules          | `application/pdf`だけ                 | PDF、PNG、JPEG、URLを種別ごとのschemaで許可     |
| Markdown見出し | `h1`〜`h3`は生成するがサイズ指定なし  | 本文基準で `h3 +2pt / h2 +4pt / h1 +6pt`        |

### metadata案

Firestoreの保存先は引き続き `users/{uid}/notes/{noteId}/materials/{materialId}` とする。`id` はdocument IDを使い、本文へ重複保存しない。

| kind       | 必須metadata                                                                           | Storage                      |
| ---------- | -------------------------------------------------------------------------------------- | ---------------------------- |
| `pdf`      | 共通field + `kind`, `contentType`, `fileName`, `pageCount`, `sizeBytes`, `storagePath` | 現行パスへPDF本体を保存      |
| `image`    | 共通field + `kind`, `contentType`, `fileName`, `sizeBytes`, `storagePath`              | 現行パスへPNG/JPEG本体を保存 |
| `bookmark` | 共通field + `kind`, `title`, `url`                                                     | 使用しない                   |

共通fieldは `createdAt`、`noteId`、`ownerUid` とする。新規PDFには `kind: "pdf"` を保存する一方、既存PDF documentには `kind` がないため、読込parserでは「`kind`なし + 現行PDF schema」をlegacy PDFとして扱う。Rulesでもlegacy PDFの許可fieldを独立した分岐に閉じ込め、画像・URLが `kind` なしで紛れ込まないようにする。

### 認証と容量

- 未ログイン時は既存どおりファイル上限10MB、永続保存なしとする。ブックマークも現在のPinia session内だけに保持する。
- ログイン時のファイル上限は既存 `getUploadLimitBytes()` / `SIGNED_IN_UPLOAD_LIMIT_BYTES` の5GBを変更しない。画像だけ別上限にする要望は今回ないため、認可方針を増やさない。
- ブックマークにはファイル容量上限を適用せず、タイトル長・URL長・schemeを検証する。
- Storage Rulesのcontent type検証はファイル内容そのもののmagic numberを保証しない。本人専用領域への保存であることを前提に、今回は既存PDFと同じMIME検証方式を維持する。必要なら後続で先頭byte検証を追加する。

### UIとアクセシビリティ

- 資料追加領域は「ファイル」「ブックマーク」の2タブまたは同等の明確な切替にする。資料パネル上部の「資料一覧 / 目次 / プレビュー」とは別の、追加方法だけを切り替えるUIとする。
- `TextbookList.vue`ではPDF、画像、URLを文言またはアイコンと文字の両方で区別し、色だけに依存しない。
- PDF・画像の行は選択ボタン、ブックマークの行は `<a>` とし、`button` と `a` を入れ子にしない。
- URL行クリックは外部タブを開くだけとし、PDF/画像の `selectedTextbookId` を上書きしない。
- 画像選択中はpreviewのみ利用可能とし、目次とページサムネイルは表示しない。ブックマークだけの一覧では目次・previewを無効にする。
- 見出しサイズは `src/styles/components/whiteboard-panel.css` に置く。`src/index.css`やglobal selectorは増やさず、既存の `.whiteboard-panel__preview` 配下へ限定する。

### 主なリスク

- `TextbookPanel.vue`は既に300行を超え、PDF読込・保存・UI制御が集中している。画像とURL処理を直接足し続けると分岐が読めなくなるため、入力UIと純粋validationを先に分離する。
- Firebase読込時に全資料へ `getDownloadURL()` を呼ぶと、Storage objectを持たないブックマークが一覧全体の失敗原因になる。ファイル資料だけURLを解決し、1件の不正metadataはskipする。
- Firestore Rulesで単一の緩い `hasOnly()` を使うと、URL documentに `storagePath`、画像documentに `url` を混在できる。kindごとに `hasOnly()` / `hasAll()` を分ける。
- 画像のobject URLをpanel unmount時に即時revokeすると、同一Pinia sessionでパネルを再表示した際にpreviewできなくなる。明示削除またはstate破棄までは保持し、今回のunmountではrevokeしない。
- `target="_blank"` だけではopener参照が残る環境があるため、`rel="noopener noreferrer"` をDOM契約テストで固定する。
- 見出しのブラウザ既定marginやfont-sizeが残ると2pt刻みにならない。既存margin resetを維持し、h1/h2/h3それぞれへ明示的なfont-sizeを指定する。

### ホワイトボード自動保存方式（推奨）

「リアルタイム保存」を、入力イベントごとのnetwork writeとは定義しない。利用者の入力は同期的にPiniaへ反映し、端末内とcloudを別周期で保存するlocal-first方式を採用する。

| Layer           | Timing                                           | Purpose                           | Cost                                 |
| --------------- | ------------------------------------------------ | --------------------------------- | ------------------------------------ |
| Pinia memory    | 入力・page操作・stroke終了時に即時               | UIとpreviewを即時更新             | network costなし                     |
| IndexedDB draft | Markdownは約300ms debounce、手書きはstroke終了後 | reload・offline・通信失敗から復元 | network costなし                     |
| Firestore page  | 最終編集から30秒後、手動保存                     | Markdown/pageを他sessionでも復元  | 1 changed pageにつき1 document write |
| Storage drawing | 最終編集から30秒後、手動保存                     | PNGと再編集用stroke dataを永続化  | upload operation + data量            |

- 同じpageの連続編集は1回へcoalesceし、ノート全体や全pageを書き直さない。
- 保存中に新しい編集が入った場合、その編集は次のdirty revisionとして残し、古いsave完了で「自動保存済み」に戻さない。
- `blur`、page切替、panel close、`visibilitychange`で待機中saveをflushする。
- `beforeunload`の非同期network完了は保証されないため、通常入力中からIndexedDBへ短い間隔で保存し、次回起動時に未同期draftを復元する。
- cloud saveはログイン済みworkspaceだけで有効にする。Workspace routeは既に永続ユーザーデータ必須である。
- 初期MVPは同時共同編集を扱わず、同じnote/pageを複数端末で編集した場合は `updatedAt` のlast-write-winsとする。競合編集UIは後続計画へ分ける。

### 保存状態と右上UI

既存 `AutosaveState = idle / dirty / saving / saved / failed` を再利用し、固定表示の「自動保存済み」をstate駆動へ置き換える。

| State            | Header UI                   | Interaction                              |
| ---------------- | --------------------------- | ---------------------------------------- |
| `idle` / `saved` | `自動保存済み` のstatus表示 | buttonではない。追加編集がない状態       |
| `dirty`          | Primaryの `保存する` button | clickでdebounce待ちをcancelして即時flush |
| `saving`         | `保存中…` のdisabled表示    | 重複click不可、`aria-live="polite"`      |
| `failed`         | `再試行` button + error補足 | local draftを維持したまま再送            |

- dirtyから30秒後に自動保存が始まるまで「保存する」buttonを表示し、利用者が画面離脱前に明示保存できる安全弁とする。
- save完了時のrevisionと現在revisionが一致した場合だけ `saved`へ遷移する。保存中に再編集された場合は `dirty`へ戻す。
- Headerは保存処理を直接実行せず `save-now`をemitし、`WorkspaceView`からノート別whiteboard storeへ委譲する。
- 保存失敗を赤いstatusだけで示さず、「再試行」文言と補足errorを併用する。

### Firestore / Storageデータ案

| Path                                                                     | Main fields                                                                              | Notes                                      |
| ------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------- | ------------------------------------------ |
| `users/{uid}/notes/{noteId}/whiteboardPages/{pageId}`                    | `ownerUid`, `noteId`, `title`, `markdown`, `createdAt`, `updatedAt`, `revision`          | 変更pageだけを`setDoc`する                 |
| `users/{uid}/notes/{noteId}/whiteboardDrawings/{drawingId}`              | `ownerUid`, `noteId`, `storagePath`, `strokesPath`, `createdAt`, `updatedAt`, `revision` | binary/large JSONをFirestoreへ直書きしない |
| `users/{uid}/notes/{noteId}/whiteboardDrawings/{drawingId}/preview.png`  | PNG blob                                                                                 | preview用、本人だけread/write              |
| `users/{uid}/notes/{noteId}/whiteboardDrawings/{drawingId}/strokes.json` | JSON blob                                                                                | 再編集用、size上限を持つ                   |

- Firestoreのtimestamp fieldはSDK `Timestamp` / `serverTimestamp()`を使用し、domainではrepository境界でISO stringへ変換する。
- `markdown`は200,000文字、`title`は120文字を初期上限とし、Firestoreの1MiB document上限へ十分な余白を残す。
- `revision`はcreate時1、保存対象のlocal content更新ごとに増やす。Rulesでは正の整数と上限を検証するが、MVPでは同時端末間のcompare-and-swapまでは行わない。
- page/drawingのcreate/updateはowner、note、parent note存在、allowed fields、型、長さ、immutable identityを両方で検証する。
- 手書きPNGとstroke JSONにはStorage Rulesでcontent type、uid path、file sizeを明示し、default denyを維持する。

### コスト評価

Firebase公式では、Cloud Firestoreの無料枠は1プロジェクトあたり1日20,000 document writesで、`set` / `update`はそれぞれ1 writeとして数えられる。料金はregionと課金通貨で変わるため、実装時は実database locationをFirebase Consoleで確認する。

- 単純に毎keypressを保存し、1秒5文字で8時間編集すると、1人だけで最大144,000 writes/dayとなり、無料枠を大幅に超える。この方式は採用しない。
- 編集後30秒間隔で保存が成立し続ける極端なケースでも、8時間で1人あたり最大960 page writes/dayが目安となる。連続入力中はtimerが更新されるため書き込みは発生しない。
- 同条件のheavy userが20人で約19,200 writes/dayとなり、ホワイトボードだけで無料枠の大半を使う。他機能のwriteもあるため、利用者増加時はUsage監視と予算alertが必要になる。
- 30秒のidle debounceで複数入力をまとめるため、実write数は上記試算より少なくなる想定だが、実測値で判断する。
- 手書きをpointer moveごとにPNG uploadするとwrite回数よりnetwork転送量・Storage operationが問題になるため、stroke終了後のlocal draftと30秒idle checkpointへまとめる。
- MVP規模では推奨方式なら「高すぎる」とは考えにくいが、数十人が長時間同時編集する段階では無料枠超過を前提にmonitoringする。

- [Firebase pricing plans（Firestore 20,000 writes/dayの無料枠）](https://firebase.google.com/docs/projects/billing/firebase-pricing-plans)
- [Cloud Firestore pricing（write課金、location別料金、usage監視）](https://cloud.google.com/firestore/pricing)

## ロールバック / フォローアップ

- UIを切り戻しても新しい画像・ブックマークdocumentやStorage objectを自動削除しない。旧clientは現行parserにより非PDFを一覧から除外するが、データ自体は残る。
- Rulesを切り戻す場合も、既存の新形式documentを読めるread権限と、本人以外を拒否するdefault denyを維持する。データを消して互換性を取らない。
- 画像追加に問題がある場合は画像用input/previewだけをfeature単位で外し、PDF repositoryとlegacy読込を維持する。
- ブックマーク追加に問題がある場合はformを一時非表示にできるが、保存済みURL documentを削除しない。安全な外部link表示が直るまでURLをplain textで表示する選択肢を取る。
- 見出しサイズに問題がある場合は `whiteboard-panel.css` の3 selectorだけを切り戻し、Markdown parserや保存済み本文を変更しない。
- cloud自動保存に問題がある場合もlocal draftを無効化せず、Headerを「保存する」の手動flush中心へ一時的に切り替える。
- debounce値はremote config化せず30秒定数とtestで管理し、Usage実測後に調整する。短くするほどwriteが増え、長くするほどcloud未同期時間が増える。
- IndexedDB migrationに失敗した場合は不正versionのdraftだけを破棄し、Firestore保存済みpageを削除・上書きしない。
- drawing uploadが片方だけ成功した場合はmetadataを完成扱いにせず、再試行またはorphan cleanup対象として記録する。
- Header表示だけを切り戻して固定「自動保存済み」へ戻すことは禁止する。保存状態が不明なら「保存状態を確認できません」と表示する。
- 後続候補:
  - 資料削除時のFirestore/Storage同時削除とobject URL revoke。
  - 画像のmagic number検証、圧縮、EXIF orientation補正、OCR。
  - ブックマークのfavicon/OGP取得をFirebase Functions経由で安全に行う仕組み。
  - ブックマーク名編集、並べ替え、フォルダー、検索。
  - 画像用サムネイル、ホワイトボードへの貼り付け。
  - 文字どおり `.jpec` という独自拡張子の対応が必要と判明した場合の別要件化。
  - 複数端末の競合検知、履歴version、共同編集、常時 `onSnapshot()`同期。
  - Usage実測に基づくadaptive debounce、管理者向けwrite予算dashboard。
